## 1. Link checker

**Summary: no internal link is broken, and no internal link points at a
URL that redirects — every internal `href` already targets its canonical,
trailing-slash destination directly. External link rot exists, as expected
for a site that aggregates ~190 outside news/research sources, but most of
what a quick scan would flag as "broken" is bot-blocking noise, not a dead
link. One genuine, fixable data bug: 8 research citations have a malformed
`doi.org` link.**

Tooling: `lychee` isn't installable via `npx` in this environment (it's a
Rust binary with no npm wrapper; `npx lychee` fails with "could not
determine executable to run"). Used **linkinator** (`npx linkinator`,
v8.1.0) instead, per the task's own fallback suggestion.

Ran two passes:
1. `npx linkinator dist --recurse` — static crawl of the built output.
2. `npx linkinator http://localhost:8792 --recurse --redirects warn` —
   crawl against `wrangler pages dev dist` (the same server used for item
   2), so internal requests go through Cloudflare Pages' actual
   routing/redirect/404 behaviour instead of linkinator's own bare static
   file server. This is the authoritative pass; numbers below are from it.

**Results:** 2,181 links checked, 2,025 OK, 156 broken.

- **Internal (relative) links: 0 broken.** Confirmed two ways — zero
  `localhost:8792`-hosted URLs came back broken, and a direct grep of
  `dist/**/*.html` for `href="..."` against every old URL in
  `docs/redirect-map.csv` (`/author/`, `/tag/`, `/category/`,
  `/news-category/`, `/my-account/`, `/feeds/`, `/newsfeeds`) found zero
  matches. No internal link issues a redirect; nothing to fix here.
- **73 "broken" hits are absolute `https://vapeindia.org/...` URLs
  (canonical tags, share-button targets, JSON-LD `@id`s) that 404 only
  because this environment tests against `localhost:8792`, not the live
  domain, and several of the pages they point at
  (`/india/nicotine-pouches/`, `/india/smokeless-tobacco/`,
  `/press/media-kit/`, every per-entry `/press/<slug>/` page) are on
  branches not yet merged to `main`/deployed. **Not a real bug** — these
  will resolve once the stack is merged and live. Listed separately so
  they don't inflate the real broken-link count.
- **83 genuinely external broken-link occurrences (81 distinct URLs).**
  Status breakdown: `403`×20, `404`×19, `400`×8, `429`×4, `401`×3, `410`×1,
  `402`×1, and `0` (connection failed outright)×27.
  - **Likely false positives — bot-blocking, not dead links** (`403`,
    `429`, `401`, `402`, and most `0`s — roughly 55 of the 83): sites like
    Bloomberg, Reuters, MarketWatch, Investing.com, eurekalert.org, and
    `vapers.org.uk` (14 occurrences alone) are known to block headless/
    automated requests. A real browser would very likely load these fine.
    Don't treat these as dead links without a manual spot-check.
  - **Likely genuinely dead (`404`, `410` — 20 of the 83):** ordinary link

    `2026-next-generation-nicotine-product-aerosol-extracts-exhibit.md`,
    `2026-oral-nicotine-pouch-continuity-programmes-and-us-college.md`,
    `2026-oral-nicotine-pouches-and-public-health-evidence-from-an.md`,
    `2026-switching-individuals-in-oud-treatment-from-cigarettes-to.md`,
    `2026-tobacco-treatment-in-the-inpatient-setting-an-american.md`. This
    is a real, fixable bug in the fetch pipeline's DOI parsing — not
    fixed here per this task's report-only scope.

## 2. Redirect / 404 testing

**Summary: every redirect rule in `public/_redirects` does exactly what it
says — when the request matches it exactly. The literal old URLs as
written in `docs/redirect-map.csv` (without a trailing slash) do NOT match
and 404 instead of redirecting, because every rule in the actual
`_redirects` file is written WITH a trailing slash and Cloudflare's
redirect engine does exact-path matching with no slash-insensitivity. The
destinations are all correct once you hit the rule as written. The
nonsense-URL check passes: a real 404, not a 200 homepage fallback.**

Served the build with `npx wrangler pages dev dist --port 8792` (installed
locally via `npm install --no-save wrangler`, since `npx wrangler` hit a
transient `EBUSY` on the shared npm cache — likely another concurrent
session on this machine). Polled `curl` until it returned 200 rather than
sleeping a fixed interval (came up on the first try).

Picked 20 URLs from `docs/redirect-map.csv`'s 38 `redirected` rows,
spread across confidence levels (high/medium/low) and destination sections
(`/`, `/news`, `/press`, `/litigation`, `/policy`, `/india`, `/india/law`,
`/about`, `/science`, `/quit`):

`/my-account/lost-password`, `/feeds/news`, `/category/news/page/2`,
`/author/avi`, `/author/samrat`, `/news-category/avi-in-news`,
`/news-category/vape-news`, `/tag/delhi-high-court`,
`/tag/e-cigarettes-policy`, `/tag/india`, `/a-history-of-tobacco`,
`/avi-events`, `/bill`, `/contact`, `/history-of-avi`, `/legal`,
`/mythbusters`, `/smokers`, `/surveys` (the one explicitly flagged
low-confidence), `/terms-and-conditions`.

**First pass — exactly as written in the CSV (no trailing slash): all 20
returned 404, not 301.** Checked `dist/_redirects` directly: every one of
these rules is stored as e.g. `/author/samrat/ → 301 /press/` — WITH a
trailing slash the CSV's own `old_url` column doesn't show. Cloudflare's
`_redirects` matching (confirmed via `wrangler pages dev`'s real engine,
not just the docs) is exact-path, with no implicit trailing-slash
normalization applied *before* a custom rule is matched — that
normalization only happens for paths that already resolve to a real
static asset/directory in `dist` (confirmed separately: `/about`,
`/india`, `/testimonials` each 308-redirect to their slash form, because
`dist/about/index.html` etc. genuinely exist; `/author/samrat` has no such
asset, so there's nothing for Cloudflare to append a slash onto before
falling through to the 404 page).

**Second pass — same 20 URLs, with the trailing slash the actual rule
uses: all 20 returned a real 301 to the correct destination.** No
mismatches.

This is worth the site owner's attention even though it isn't strictly a
"wrong destination" bug: if any real inbound link, bookmark, or search
result references one of these old WordPress URLs *without* its trailing
slash, it will hit a 404 instead of being redirected. In practice WordPress
itself typically 301s a non-slash request to the slash form before a
visitor even leaves the old site, and Google tends to index the canonical
(slash) form — so most real-world traffic is probably unaffected — but
this isn't guaranteed for every inbound link (a hand-typed URL, an old
cached/non-canonical indexed variant, a backlink constructed without the
slash). Flagging as a real gap, not fixing it (would mean editing
`public/_redirects`, out of scope for this audit).

**Cross-checks**, all behaving as documented:
- `skipped` rows (`/sitemap.html`, `/wp-admin`, `/blocks/auto-draft`) → 404,
  correctly un-redirected.
- `NEEDS DECISION` rows (`/shop`, `/privacy-policy`, `/vaper-registration`)
  → 404, correctly left unhandled pending the site owner's call.
- `already-correct` rows (`/about`, `/india`, `/testimonials`) → 308 to
  their own slash form (Cloudflare's own static-asset trailing-slash
  behaviour, not a `_redirects` rule), then 200.
- **Nonsense URL** (`/this-page-definitely-does-not-exist-zzz12345`) →
  real `404`, served from `dist/404.html` (confirmed by body content —
  the actual "This page doesn't exist" copy, not a 200 homepage
  fallback). The `_redirects`-cap failure mode CLAUDE.md documents (a
  dropped rule silently falling through to a 200 homepage) is **not**
  happening here — `98` rules currently parse (`wrangler`'s own "Parsed 98
  valid redirect rules" log line), comfortably under the ~107 ceiling.

## 3. Content guard — whole-site sweep

**Summary: 10 real hits, all either sourced government/economic
statistics being caught by the price-pattern check or two brand names
(IQOS, JUUL) named factually in formal government submissions, neither
really a drafting-note or advertising problem. Zero drafting-note leaks,
zero trailing-slash violations, zero `reviewed:false` entries leaking into
the live build — all three checked across the *entire* current site, not
just a diff.**

**Methodology note, read before trusting the number:** the task's
suggested invocation,
`node scripts/ci-content-guard.mjs 4b825dc642cb6eb9a060e54bf8d69288fbee4904`
(the empty-tree hash), **does not actually run** — verified, not assumed.
`ci-content-guard.mjs`'s `getAddedLines()` calls
`git diff --unified=0 ${base}...HEAD` (triple-dot), and triple-dot
requires a *commit* on both sides for its merge-base calculation:
- The empty-tree hash is a tree object, not a commit, so git refuses
  outright: `error: object ... is a tree, not a commit`.
- Wrapping it in a throwaway orphan commit (`git commit-tree
  4b825dc6...`) fixes that type error but immediately hits a second one:
  `fatal: ...: no merge base` — an orphan commit shares no history with
  `HEAD` by definition, and triple-dot needs a common ancestor to diff
  from, not just two valid commits.

Neither failure is fixable without editing `ci-content-guard.mjs` itself
(out of scope — this audit doesn't touch that file) or rewriting this
branch's real history to graft an empty-tree root onto it (destructive,
not acceptable). So two things were done instead, and they agree exactly:

1. **Ran the real script unmodified**, using the repository's actual root
   commit (`272c403574b07ae7f0e47a91f8cf4b8d5198c087`, "Initial scaffold")
   as `<base-ref>` — a genuine ancestor of `HEAD`, so triple-dot resolves
   cleanly. This captures 16,331 of the current content/page lines as
   "added" (confirmed by direct line count against `find src/content
   src/pages -type f` → 1,008 files today). The gap: that first commit
   wasn't actually empty — it already held 69 press entries, all 8
   litigation entries, 1 research entry, and 14 page templates (84 files,
   1,613 lines), so a line in one of those 84 files that's never changed
   since wouldn't show up as "added" here and could theoretically hide a
   pre-existing violation.
   → **Result: 10 violations.**
2. **To close that gap, wrote a small supplementary script**
   (not a modification of `ci-content-guard.mjs`) that copies its exact
   check 1/2/3/4 regexes verbatim and applies them to the **full current
   text of every file** under `src/content` and `src/pages` (1,008 files),
   independent of git history entirely — true 100% coverage, including
   those 84 original files.
   → **Result: also exactly 10 violations, identical list.** The
   root-commit substitute wasn't hiding anything.

Check 5 (`reviewed:false` leaking into the build) ran as part of the
normal script invocation too — it always checks `dist/` directly,
regardless of `baseRef` — and found **zero leaks**: none of the
unreviewed drafts (the 4 pending press statements from PR #14, any
`reviewed:false` research/testimonial entries) built a live page.

## 5. Metadata audit

**Summary: near-perfect. 204 pages scanned. Trailing-slash canonicals:
